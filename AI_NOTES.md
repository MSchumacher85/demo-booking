# Использование ИИ

## Инструменты и промпты

Использовал OpenAI Codex для анализа исходной реализации, подготовки исправлений и автоматических тестов. При работе учитывались проектные правила Laravel Boost, исходники установленных пакетов и официальная документация Laravel, PHPUnit и PostgreSQL. Для проверки использовались PHPUnit в Docker на PostgreSQL, Laravel Pint и ручные запросы через Postman.

### Содержание задач

Ниже приведено редакционное изложение обсуждавшихся задач; дословные запросы из переписки вынесены в следующий раздел.

**1. Анализ проекта и план реализации**

>Проанализируй README и код проекта. Найди ошибки, оцени их серьёзность и составь план исправлений. Отдельно объясни, какие подозрительные места на самом деле работают правильно.

**2. Проверка безопасности SQL-запросов**

> Проверь, возможна ли SQL-инъекция, проанализируй построение SQL-запроса в методе store. Проверь возможность SQL-инъекции через входные параметры, исправь запрос. Добавь тесты обработки некорректного ввода.

**3. Защита от конкурентного бронирования**

> Давай исправим гонку при создании брони. Используй транзакцию и блокировку переговорной. Добавь тесты одновременных запросов: пересекающиеся брони, соседние интервалы и бронирование разных комнат

## Ошибка ИИ и перепроверка предложений

Предложенная ИИ команда запуска тестов завершилась ошибкой: параметр --no-interaction был передан в PHPUnit, который его не поддерживает. По выводу команды обнаружили проблему и перешли на прямой запуск php vendor/bin/phpunit.

Отдельно уточнил соответствие валидации дат требованиям задания. Поддерживаемые формы ISO 8601 явно описаны в README: календарная дата, часы, минуты и обязательное смещение. Выбранный формат отделён от бизнес-правил длительности, шага и рабочего времени офиса.

Предложения по коду проверялись поведением API и состоянием БД. До исправления `destroy` новые тесты удаления чужой брони получали 204 вместо ожидаемого 403. После добавления проверки автора они прошли. Тесты создания отдельно проверяют фиксированные ожидаемые значения UTC для разных смещений и офисов, а также соседние интервалы, вложения и границы рабочего дня.

Для бонуса сначала было подготовлено описание решения в README, затем я предложил реализовать защиту. Агент написал конкурентный тест с двумя отдельными PHP-процессами. До исправления тест получил два ответа 201 для одного слота; после добавления транзакции и блокировки комнаты — 201 и 422, с одной бронью в базе. Это подтверждает, что тест воспроизводит исходную гонку.

## Что проверял самостоятельно

- Через Postman вручную проверил создание брони (`POST /api/bookings`), удаление (`DELETE /api/bookings/{id}`) и получение списка броней (`GET /api/bookings`).
- Самостоятельно запускал исходные тесты через Docker Compose командой `docker compose exec app php artisan test --compact`.
- Перед коммитами разбирал обоснованность изменений: определение автора по авторизации, проверку прав на отмену, обработку смещений времени, защиту SQL-запросов и контекст логирования.
- Ручную проверку API, выбор файлов и создание коммитов с исправлениями выполнял самостоятельно. Предложение ИИ ограничиться описанием гонки пересмотрел в пользу реализации с конкурентным тестом.

## Проверки, выполненные агентом

После исправлений создания, отмены и защиты от одновременного бронирования агент выполнил полный прогон:

```sh
docker compose exec -T app php vendor/bin/phpunit --no-progress
```

Результат: **81 тест, 358 проверок, успешно**. Тесты используют отдельную базу PostgreSQL `testing`. Форматирование изменённых PHP-файлов через Pint также прошло.

После реализации защиты от гонки отдельный прогон `BookingConcurrencyTest` прошёл: **3 теста, 21 проверка**. Каждый запрос проходит через HTTP-ядро Laravel в своём процессе и использует настоящее отдельное соединение с PostgreSQL и Bearer-токен. Проверяются конфликтующие запросы, соседние интервалы и независимость разных комнат. Это автоматическая проверка конкуренции на уровне приложения и БД; она не заменяет нагрузочное тестирование HTTP-сервера.
