## Запуск

Нужны Docker и Docker Compose. Команды выполняются из корня проекта. Приложение предоставляет API; интерфейса бронирования нет.

Первоначальный запуск и загрузка демонстрационных данных:

```sh
docker compose up -d --wait
docker compose exec app php artisan migrate:fresh --seed --no-interaction
```

Первый запуск занимает несколько минут: контейнер создаёт `.env` из `.env.example`, устанавливает зависимости и генерирует ключ приложения. API доступно по адресу `http://localhost:8000/api`.

`migrate:fresh --seed` удаляет существующие таблицы базы приложения и заново создаёт демонстрационные данные. Для обычного запуска, в том числе после перезагрузки компьютера, достаточно:

```sh
docker compose up -d --wait
```

Данные PostgreSQL сохраняются в Docker volume.

## Тесты

```sh
docker compose exec -T app php vendor/bin/phpunit --no-progress
```

Тесты идут на PostgreSQL в отдельной базе `testing`, которую Docker создаёт при инициализации тома. Для запуска только тестов отмены бронирования:

```sh
docker compose exec -T app php vendor/bin/phpunit tests/Feature/BookingDestroyTest.php --no-progress
```

Feature-тесты проверяют создание и отмену через HTTP-слой Laravel и состояние базы: пересечения и соседние интервалы, длительность и шаг, рабочие часы обоих офисов, смещения и сохранение UTC, некорректный ввод, авторство и освобождение слота после отмены. Прошедшие даты и выходные разрешены и покрыты тестом.

Проверки одновременного бронирования запускают два отдельных PHP-процесса, каждый со своим HTTP-ядром Laravel, Bearer-токеном и соединением с PostgreSQL. Они включены в общий прогон. Для отдельного запуска:

```sh
docker compose exec -T app php vendor/bin/phpunit tests/Feature/BookingConcurrencyTest.php --no-progress
```

В этом классе используется `DatabaseMigrations`: данные должны быть зафиксированы в тестовой базе и видны дочерним процессам, поэтому оборачивать весь тест в транзакцию, как при `RefreshDatabase`, нельзя. Рабочая база `booking` в тестах не используется.

## API

Все методы требуют заголовки `Authorization: Bearer <токен>` и `Accept: application/json`. Без `Accept` запрос без токена вернёт 500 вместо 401.

| Метод | Адрес | Что делает |
| --- | --- | --- |
| GET | `/api/bookings` | Мои брони |
| POST | `/api/bookings` | Создать бронь |
| DELETE | `/api/bookings/{id}` | Отменить бронь |
| GET | `/api/rooms/{room}/bookings/today` | Брони комнаты на сегодня |

### Создание брони

Обязательные поля: `room_id`, `title`, `starts_at`, `ends_at`. Автор определяется по токену; переданный клиентом `user_id` игнорируется. Офис и его часовой пояс определяются по переговорной `room_id`.

Тело запроса для Postman (Body → raw → JSON):

```json
{
  "room_id": 1,
  "title": "Планёрка",
  "starts_at": "2026-11-02T10:00:00+03:00",
  "ends_at": "2026-11-02T11:00:00+03:00"
}
```

Эквивалентный пример для shell с поддержкой переноса строки через `\`:

```sh
curl -X POST http://localhost:8000/api/bookings \
  -H "Authorization: Bearer anna-token" \
  -H "Accept: application/json" \
  -H "Content-Type: application/json" \
  -d '{"room_id": 1, "title": "Планёрка", "starts_at": "2026-11-02T10:00:00+03:00", "ends_at": "2026-11-02T11:00:00+03:00"}'
```

### Формат времени и правила

Принимается календарная дата `YYYY-MM-DD`, затем `T`, часы и минуты `HH:MM` и обязательное смещение: `Z`, `+HH:MM`, `-HH:MM`, `+HHMM` или `-HHMM`. Можно указать секунды и от 1 до 6 цифр дробной части секунды через точку. Например, `2026-11-02T10:00+03:00` и `2026-11-02T10:00:00.000000+0300` обозначают одно время. Это поддерживаемые формы ISO 8601; другие формы записи даты не принимаются.

Смещения начала и конца могут отличаться. Длительность считается между фактическими моментами времени и должна быть от 15 минут до 4 часов включительно. Затем обе даты переводятся в часовой пояс офиса: весь интервал должен попасть в 09:00–20:00 одного местного дня, минуты обеих границ должны быть кратны 15, секунды и доли секунды — равны нулю. Время не округляется.

Для сравнения пересечений и сохранения обе даты нормализуются в UTC. Например, московская встреча 10:00–11:00 с `+03:00` хранится как 07:00–08:00 UTC. В столбцах `timestamp without time zone` используется соглашение о хранении UTC; старые записи, созданные исходной версией с потерей смещения, автоматически не исправляются.

### Ответы создания и отмены

| Ситуация | Ответ |
| --- | --- |
| Бронь создана | `201`, JSON с данными брони и временем в UTC |
| Некорректные поля, нарушение правил времени или пересечение | `422`, поля `message` и `errors` с сообщениями валидации |
| Автор отменил свою бронь | `204`, пустое тело |
| Другой пользователь пытается отменить бронь | `403`, сообщение «Отменить бронь может только её автор.» |
| Отменяемая бронь отсутствует или её ID некорректен | `404` |
| Нет авторизации при заголовке `Accept: application/json` | `401` |

Для отмены передаётся ID брони в `DELETE /api/bookings/{id}`; тело запроса не требуется.

Лог созданных броней пишется в `storage/logs/bookings.log`.

Логика методов `index` и `today` оставлена без изменений по условиям задания. Их проблемы и разбор исходной реализации находятся в [REVIEW.md](REVIEW.md). Использование ИИ и выполненные проверки описаны в [AI_NOTES.md](AI_NOTES.md).

## Защита от одновременного бронирования

Проверка пересечений и создание брони выполняются в одной транзакции с блокировкой строки переговорной. Без этой блокировки оба одновременных запроса могли получить `false` от `exists()` до сохранения первой брони и затем оба выполнить вставку.

Порядок действий в `store`:

1. Открывается `DB::transaction(...)`.
2. Выбранная комната загружается через `Room::query()->lockForUpdate()->findOrFail(...)`.
3. После получения блокировки проверяются пересечения в этой комнате по UTC: `starts_at < new_end AND ends_at > new_start`.
4. При конфликте выбрасывается `ValidationException` с ответом 422; иначе бронь создаётся в той же транзакции.
5. После успешного завершения транзакции записывается лог создания.

Такое применение `lockForUpdate()` внутри транзакции соответствует механизму [пессимистических блокировок Laravel](https://laravel.com/framework/docs/13.x/queries#pessimistic-locking).

Второй запрос на ту же комнату ждёт завершения первой транзакции. При стандартном для PostgreSQL уровне изоляции [READ COMMITTED](https://www.postgresql.org/docs/17/transaction-iso.html#XACT-READ-COMMITTED) его последующая проверка пересечений видит уже сохранённую бронь. Запросы на другие комнаты могут работать независимо. Блокировка строки удерживается до конца транзакции, см. [PostgreSQL: блокировки строк](https://www.postgresql.org/docs/17/explicit-locking.html#LOCKING-ROWS).

Блокировать нужно именно комнату: она существует и тогда, когда в ней ещё нет ни одной брони. Блокировка найденных броней не защищает пустой результат поиска. Одна транзакция без блокировки также не устраняет промежуток между проверкой и вставкой. Все пути создания или изменения интервала брони должны соблюдать тот же порядок блокировки и проверки.

`BookingConcurrencyTest` проверяет три сценария:

- Два запроса на один свободный слот: один ответ 201, один 422 и ровно одна бронь в базе.
- Два запроса на смежные интервалы: оба получают 201 и сохраняются.
- Заблокированная комната не задерживает бронирование другой комнаты.

Для воспроизведения гонки тест удерживает блокировку `SHARE` на таблице `bookings`: она разрешает чтение, но задерживает вставку. После того как оба процесса дошли до ожидания блокировок, тест снимает барьер. Готовность определяется через `pg_stat_activity`, с ограничением времени ожидания. На версии без исправления этот же тест получил два ответа 201, поэтому он обнаруживает исходную гонку, а не просто проверяет последовательные запросы.

Блокировка всей таблицы используется только для синхронизации теста. В приложении блокируется одна строка комнаты. Защита относится к пути создания через API; прямые записи в БД и будущие способы изменения брони должны отдельно соблюдать это правило.
